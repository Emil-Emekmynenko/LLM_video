# Техническое задание: платформа подготовки, упаковки и доставки медиаассетов

**Версия:** 1.0  
**Дата:** 2026-09-19  
**Статус:** исходное ТЗ для проектирования и разработки  
**Целевая команда разработки:** Codex под контролем владельца продукта  
**Рабочее название:** Media Dataset Factory

---

## 1. Назначение документа

Документ определяет требования к внутренней веб-платформе, которая принимает исходные видео, анализирует их содержание, при необходимости создаёт озвучку, получает транскрипт из финального мастер-файла, формирует метаданные, проверяет комплект и доставляет его в хранилище заказчика.

Платформа создаётся как внутренний производственный инструмент. Она должна быть пригодна для последующего развития в многопользовательский коммерческий SaaS, однако функции биллинга, публичной регистрации и самостоятельного подключения внешних клиентов не входят в первый релиз.

Главный результат работы платформы — не текстовое описание само по себе, а проверенный и целостный комплект файлов, готовый к машинной обработке заказчиком.

---

## 2. Контекст и продуктовая формулировка

Платформа автоматизирует услугу по подготовке медиадатасетов:

> Исходное медиа преобразуется в готовый к употреблению комплект, содержащий мастер-файл, машиночитаемую аннотацию и метаданные, после чего комплект проходит автоматический и операторский контроль и безопасно доставляется заказчику.

Единица учёта, проверки и доставки — **комплект**, а не отдельный файл.

Комплект считается доставленным только после того, как:

1. все обязательные файлы сформированы;
2. все проверки пройдены;
3. медиа загружено в хранилище заказчика;
4. сопроводительные файлы загружены после медиа;
5. удалённые файлы побайтово сверены с локальными по хешу;
6. установлен момент `package_complete_at`.

## 3. Термины

| Термин | Определение |
|---|---|
| Ассет | Исходный или финальный медиафайл: видео, изображение или документ. MVP работает только с видео. |
| Комплект | Мастер-файл и связанные с ним транскрипт, метаданные и манифест. |
| Исходник | Файл, принятый платформой до каких-либо преобразований. |
| Мастер | Финальный медиафайл, который будет передан заказчику. |
| Proxy | Временная уменьшенная копия, используемая только для машинного анализа. |
| Sidecar | Сопроводительный файл рядом с медиа: транскрипт, метаданные или манифест. |
| VLM | Vision-Language Model, анализирующая видеоряд и генерирующая структурированное описание. |
| ASR | Система распознавания речи. |
| Forced alignment | Уточнение начала и конца каждого распознанного слова по аудиодорожке. |
| TTS | Синтез речи по подготовленному сценарию. |
| Схема заказчика | Версионируемое описание обязательных файлов, полей, типов и правил доставки. |
| Поставка | Группа комплектов, передаваемая заказчику как одна партия. |

## 4. Цели

### 4.1. Цели MVP

Платформа должна позволять оператору:

1. загрузить одно или несколько видео;
2. сохранить исходники без изменения;
3. получить технические параметры и хеш каждого файла;
4. обнаружить точные дубли;
5. автоматически проанализировать содержание видео;
6. получить черновые `Title`, `Description`, `Category`, главы и действия;
7. при необходимости создать и добавить озвучку;
8. снять транскрипт именно с финального мастер-файла;
9. получить тайминги каждого слова;
10. сформировать метаданные по выбранной схеме;
11. дать оператору проверить и исправить машинный результат;
12. выполнить автоматическую приёмку комплекта;
13. скачать готовый комплект локально;
14. после пилотного этапа — доставить комплект в S3- или GCS-совместимое хранилище;
15. отобразить фактическое состояние обработки и доставки.

### 4.2. Долгосрочные цели

- несколько заказчиков и схем поставки;
- массовая обработка;
- API для внешних систем;
- подключаемые модели VLM, ASR, alignment и TTS;
- накопление исправлений операторов для дообучения;
- отчётность по качеству, затратам и производительности;
- развёртывание в изолированном контуре заказчика;
- развитие во внешний SaaS без переписывания ядра pipeline.

### 4.3. Не цели MVP

В MVP не входят:

- обучение фундаментальной модели с нуля;
- гарантированное распознавание абсолютно всех действий любого типа;
- покадровая промышленная видеоаналитика в реальном времени;
- распознавание личности по лицу;
- биллинг и тарифы;
- публичная регистрация клиентов;
- мобильное приложение;
- совместное редактирование в реальном времени;
- автоматическое удаление или перезапись файлов в хранилище заказчика;
- поддержка изображений и документов, кроме архитектурной готовности к их добавлению.

## 5. Основные принципы

### 5.1. Неизменяемость исходника

- Исходник сохраняется в неизменном виде.
- Для исходника рассчитывается SHA-256.
- Операции анализа выполняются над временным proxy, если это экономит ресурсы.
- Proxy не включается в комплект и может быть удалён по политике хранения.
- Любое изменение мастер-файла создаёт новую версию, а не перезаписывает предыдущую.

### 5.2. Видеопоток не перекодируется без явного разрешения

- Если к видео добавляется или заменяется аудиодорожка, видеопоток копируется с `-c:v copy`.
- Если контейнер не позволяет выполнить операцию без перекодирования, pipeline останавливается с объяснимой ошибкой или запрашивает утверждённый профиль преобразования.
- Автоматическое скрытое перекодирование запрещено.

### 5.3. Технические факты определяются кодом, а не нейросетью

VLM запрещено использовать как источник следующих полей:

- длительность;
- разрешение;
- частота кадров;
- кодеки;
- наличие аудиодорожек;
- размер файла;
- контрольная сумма;
- WPM.

Эти значения вычисляются из реальных артефактов через FFmpeg/ffprobe, файловую систему и транскрипт.

### 5.4. Транскрипт создаётся из финального мастера

- Сценарий озвучки не считается транскриптом.
- После создания или замены озвучки ASR и alignment запускаются заново по финальному мастеру.
- В поставку не может попасть транскрипт, полученный из промежуточного файла.

### 5.5. Комплект доставляется атомарно на уровне бизнес-логики

- Сначала загружается медиа.
- После подтверждения загрузки медиа загружаются sidecar-файлы.
- При ошибке комплект остаётся незавершённым.
- Статус `complete` устанавливается только после удалённой сверки всех файлов.

### 5.6. Машина предлагает, человек утверждает

- До накопления подтверждённых метрик обязательные семантические поля проходят операторскую проверку.
- Исправления оператора сохраняются отдельно от машинного ответа.
- Оригинальный ответ модели не перезаписывается.

## 6. Пользователи и роли

### 6.1. Оператор

- загружает файлы;
- заполняет известные атрибуты;
- запускает обработку;
- проверяет и исправляет метаданные, главы, действия и сценарий;
- отправляет комплект на валидацию;
- инициирует доставку утверждённого комплекта.

### 6.2. Контролёр качества

- видит результаты автоматической проверки;
- просматривает изменения оператора;
- утверждает или отклоняет комплект;
- фиксирует причину брака;
- может вернуть комплект на конкретный этап.

### 6.3. Администратор

- управляет пользователями и ролями;
- создаёт заказчиков и версии схем;
- настраивает модели и хранилища;
- управляет справочниками категорий;
- видит технические логи и системные метрики;
- управляет политиками хранения.

### 6.4. Сервисный аккаунт

- используется фоновыми workers;
- имеет минимально необходимые права;
- не используется человеком для входа;
- его секреты не отображаются в интерфейсе и логах.

## 7. Пользовательские сценарии

### UC-01. Создание пилотного комплекта

1. Оператор создаёт поставку.
2. Выбирает заказчика и версию схемы.
3. Загружает видео.
4. Заполняет достоверные атрибуты: страна, участник, сессия, категория или оставляет неизвестные значения пустыми.
5. Система инспектирует файл и ищет дубли.
6. Система создаёт proxy и анализирует содержание.
7. Оператор проверяет предложенные метаданные.
8. Если нужна озвучка, оператор утверждает сценарий и запускает TTS.
9. Система собирает мастер без перекодирования видеопотока.
10. Система распознаёт финальную дорожку и выполняет word alignment.
11. Система формирует комплект и выполняет проверки.
12. Контролёр утверждает комплект.
13. Оператор скачивает ZIP или инициирует доставку.

### UC-02. Отказ из-за отсутствия таймингов слов

1. ASR вернул только сегменты или alignment завершился ошибкой.
2. Валидатор устанавливает код `no_word_timings` или `invalid_word_timing`.
3. Комплект получает статус `validation_failed`.
4. Кнопка доставки недоступна.
5. Оператор видит причину и может перезапустить транскрибацию.

### UC-03. Обнаружение точного дубля

1. После загрузки рассчитывается SHA-256.
2. Найден существующий ассет с тем же хешем.
3. Система не запускает дорогостоящую обработку автоматически.
4. Оператор видит ссылку на найденный ассет.
5. Продолжение возможно только с явно зафиксированным решением и причиной.

### UC-04. Возобновление оборванной доставки

1. Загрузка большого медиа обрывается.
2. Система сохраняет идентификатор resumable-сессии и загруженный диапазон.
3. Worker возобновляет передачу, не начиная файл заново.
4. Sidecar-файлы не загружаются до окончания медиа.

### UC-05. Повторная обработка новой моделью

1. Администратор активирует новую версию VLM или промпта.
2. Оператор создаёт новый analysis run.
3. Старый машинный результат сохраняется.
4. Новая версия не изменяет ранее утверждённый комплект без явного действия пользователя.

## 8. Состав комплекта

### 8.1. Обязательные файлы MVP

```text
<Base>.mp4
<Base>_transcript.json
<Base>_metadata.json
<Base>_manifest.json
```

`manifest.json` является внутренним обязательным файлом платформы. Его включение в поставку заказчику определяется схемой заказчика.

### 8.2. Базовое имя

Базовое имя должно быть содержательным:

```text
<Category>_<Title>
```

Пример:

```text
Repairs_And_DIY_Fixing_Table_Leg.mp4
```

Требования:

- имя не строится только из UUID;
- для внешней поставки используется безопасный набор символов, заданный схемой;
- технический идентификатор не добавляется к имени, если уникальность обеспечивается путём;
- итоговое имя проходит предварительный просмотр оператором;
- переименование обновляет имена всех файлов комплекта атомарно до начала доставки.

### 8.3. Раскладка в хранилище

По умолчанию:

```text
<delivery-date>/<country>/<participant>/<session>/
    <Base>.mp4
    <Base>_transcript.json
    <Base>_metadata.json
    <Base>_manifest.json
```

Правила:

- `delivery-date` — дата поставки, а не дата съёмки;
- отсутствующий или недостоверный уровень пути не создаётся;
- `unknown`, пустая строка и фиктивная страна не подставляются автоматически;
- схема пути конфигурируется для каждого заказчика;
- перед загрузкой отображается полный список удалённых ключей;
- существующий ключ не перезаписывается.

## 9. Функциональные требования

### FR-001. Создание поставки

Система должна позволять создать поставку со следующими полями:

- внутренний UUID;
- заказчик;
- версия схемы;
- плановая дата поставки;
- комментарий;
- ответственный оператор;
- статус;
- даты создания и изменения.

### FR-002. Загрузка медиа

- Поддержать `.mp4`, `.mov`, `.mkv`, если разрешено схемой.
- Для MVP минимальный гарантированный формат — MP4.
- Поддержать файлы размером не менее 6 ГиБ.
- Загрузка в платформу должна быть возобновляемой либо выполняться через подключённое внутреннее хранилище.
- Файл должен записываться под внутренним UUID, сохраняя оригинальное имя как атрибут.
- После загрузки должна выполняться проверка размера и SHA-256.

### FR-003. Инспекция медиа

Система должна получить через ffprobe:

- длительность;
- контейнер;
- видео- и аудиокодеки;
- разрешение;
- SAR/DAR;
- частоту кадров;
- количество и параметры дорожек;
- наличие повреждений, доступных для выявления декодированием;
- размер файла.

Результат сохраняется как версионируемый технический отчёт.

### FR-004. Поиск дублей

- Основной критерий точного дубля — SHA-256 полного файла.
- Совпадение имени не является доказательством дубля.
- В будущем допускается отдельный near-duplicate detector, но он не заменяет точный хеш.

### FR-005. Создание proxy

- Proxy создаётся только для внутреннего анализа.
- Параметры proxy конфигурируются.
- Proxy должен сохранять длительность и временную шкалу исходника.
- Любое смещение временной шкалы считается ошибкой.
- Связь proxy с исходником и командой создания сохраняется.

### FR-006. Разбиение на сцены и фрагменты

- Использовать детектор сцен и временное разбиение.
- Слишком длинные сцены делить на клипы настраиваемой длины.
- Значения по умолчанию: клип 15 секунд, перекрытие 2 секунды.
- Для каждого клипа хранить абсолютные `start` и `end`.
- Не создавать поставочные файлы из этих клипов: это внутренние единицы анализа.

### FR-007. Анализ содержимого VLM

Для каждого клипа VLM должна возвращать структурированный ответ:

- краткое резюме;
- видимые участники без идентификации личности;
- действия;
- объекты;
- предлагаемые главы;
- фактическое визуальное свидетельство;
- уверенность модели;
- признаки неопределённости.

Требования:

- ответ валидируется по JSON Schema;
- модель инструктируется описывать только наблюдаемое;
- речь не считается выполненным действием;
- намерения людей не угадываются;
- допустимо значение `unknown_action`;
- сохраняются модель, ревизия весов, параметры инференса, версия промпта и время выполнения;
- невалидный JSON автоматически повторяется ограниченное число раз, после чего требует проверки.

### FR-008. Объединение событий

Система должна:

- переводить относительные таймкоды в абсолютные;
- объединять события из перекрывающихся клипов;
- сохранять связь итогового события с исходными наблюдениями;
- не удалять конфликтующие события без следа;
- позволять оператору разделять, объединять, удалять и редактировать события.

### FR-009. Формирование семантических метаданных

На основе утверждённого анализа система предлагает:

- `Title`;
- `Description`;
- `Category` из справочника;
- главы;
- язык предполагаемой озвучки, если создаётся новый сценарий.

Оператор обязан подтвердить семантические поля до сборки комплекта, если для конкретной схемы не включён утверждённый режим автоприёмки.

### FR-010. Сценарий озвучки

Если озвучка нужна, система должна:

- создать сценарий, соответствующий фактически видимым действиям;
- обеспечить настраиваемый стиль, язык и целевую скорость речи;
- показать сценарий оператору;
- хранить версии и правки;
- запретить генерацию TTS из неутверждённого сценария в MVP.

### FR-011. Формирование мастер-файла

Должны поддерживаться режимы:

1. сохранить исходную аудиодорожку;
2. удалить исходную аудиодорожку;
3. заменить её синтетической или дикторской;
4. добавить дополнительную дорожку, если это разрешено схемой.

Правила:

- выбор режима хранится как явное решение;
- видеопоток копируется без перекодирования;
- полученный мастер повторно инспектируется;
- SHA-256 мастера вычисляется после завершения сборки;
- мастер не считается готовым, пока не подтверждена корректность декодирования.

### FR-012. Сопоставление отдельно полученной аудиодорожки

- Основной автоматический сигнал — совпадение длительности в пределах настраиваемого допуска.
- Имя файла является вспомогательным сигналом.
- При нескольких подходящих кандидатах требуется выбор оператора.
- Выбранное сопоставление и разница длительностей записываются в аудит.

### FR-013. Распознавание речи

- ASR запускается по финальному мастеру.
- Для MVP предусмотреть локальный backend на базе faster-whisper или совместимого провайдера.
- Сохранять язык, вероятность определения языка, сегменты и текст.
- Параметры модели и версия сохраняются.
- Результат ASR является промежуточным до выполнения word alignment.

### FR-014. Тайминги слов

- Каждое поставляемое слово должно иметь `start` и `end`.
- Тайминги должны быть числовыми, конечными, неотрицательными и не выходить за длительность медиа с учётом конфигурируемой погрешности.
- `end >= start`.
- Слова внутри сегмента должны идти в неубывающем порядке.
- Отсутствие word timings вызывает блокирующую ошибку `no_word_timings`.
- Некорректные значения вызывают `invalid_word_timing`.
- Если ASR не обеспечивает нужную точность, применяется отдельный forced-alignment backend.

### FR-015. Метаданные

Базовая схема:

| Поле | Источник |
|---|---|
| `Title` | утверждённое оператором семантическое поле |
| `Description` | утверждённое оператором семантическое поле |
| `Publication Date` | правило схемы: дата съёмки либо поставки |
| `Category` | справочник заказчика |
| `Duration` | финальный мастер, ffprobe |
| `Language` | фактический язык финальной аудиодорожки |
| `Resolution` | финальный мастер, ffprobe |
| `WPM` | поставляемый транскрипт и фактическая длительность |

Требования:

- схема и порядок сериализации ключей версионируются;
- неизвестное значение записывается как `null`, если схема не запрещает это;
- `0`, `""` и `null` не взаимозаменяемы;
- вычисляемые поля пересчитываются перед каждой сборкой;
- ручное редактирование технических полей запрещено либо явно маркируется как override с причиной;
- язык интерфейса оператора не влияет на `Language`.

### FR-016. Расчёт WPM

По умолчанию:

```text
WPM = количество поставляемых слов / (длительность финального мастера в секундах / 60)
```

Схема заказчика может переопределить знаменатель, например использовать только речевые интервалы. Метод расчёта и версия алгоритма должны сохраняться.

### FR-017. Редактор результатов

Интерфейс проверки должен включать:

- видеоплеер с переходом по таймкоду;
- форму метаданных;
- таблицу событий;
- редактор глав;
- редактор сценария;
- просмотр транскрипта по словам;
- подсветку ошибок валидации;
- сравнение машинного и исправленного результата;
- сохранение черновика;
- историю изменений.

### FR-018. Сборка комплекта

- Все файлы строятся из одной зафиксированной версии мастера.
- Базовые имена должны совпадать.
- JSON сериализуется детерминированно с требуемым порядком ключей.
- Сборка получает уникальную версию.
- Повторная сборка не перезаписывает утверждённую версию.

### FR-019. Автоматическая валидация

Обязательные блокирующие проверки:

1. все обязательные файлы присутствуют;
2. базовое имя у файлов совпадает;
3. каждое слово имеет тайминги;
4. транскрипт относится к текущему хешу мастер-файла;
5. слова находятся внутри временной шкалы мастера;
6. метаданные соответствуют JSON Schema и правилам nullability;
7. вычисляемые поля совпадают с реальными артефактами;
8. мастер декодируется, а его параметры совпадают с метаданными;
9. точного дубля в текущей поставке нет либо есть утверждённое исключение;
10. имена и путь безопасны;
11. аудиополитика соответствует схеме;
12. операторская и QA-проверка выполнены, если они обязательны.

Валидатор должен возвращать массив ошибок с кодом, уровнем, путём к полю и человекочитаемым сообщением. Валидатор не должен молча исправлять поставочные данные.

### FR-020. Манифест

Манифест должен содержать:

- идентификатор комплекта и поставки;
- версию сборки;
- заказчика и версию схемы;
- список файлов;
- размер и SHA-256 каждого файла;
- MIME type;
- локальный и целевой относительный путь;
- хеш мастер-файла, из которого создан транскрипт;
- версии моделей и промптов;
- результаты валидации;
- время сборки;
- идентификаторы утверждающих пользователей.

### FR-021. Локальный экспорт

- Экспортировать комплект как ZIP или как директорию.
- ZIP строится потоково без полной копии больших файлов в оперативную память.
- Имя архива включает идентификатор поставки и версию.
- Скачивание доступно только после успешной валидации.

### FR-022. Доставка в объектное хранилище

- Поддержать адаптеры GCS и S3-совместимого API.
- Архитектура должна допускать R2 и другие S3-совместимые сервисы.
- Большие файлы загружаются resumable/multipart-механизмом.
- Рекомендуемый размер части по умолчанию — 32 МиБ, параметр конфигурируется.
- Медиа загружается раньше sidecar-файлов.
- Существующие объекты не перезаписываются.
- Удаление удалённых объектов отсутствует в штатном pipeline.
- Если требуется клиентское шифрование, оно применяется ко всем обязательным файлам по версии схемы.
- После загрузки выполняется удалённая проверка размера и криптографического хеша либо эквивалентной подтверждённой контрольной суммы.

### FR-023. Учёт состояния доставки

Хранить минимум:

- `delivered_at` — пользователь инициировал доставку;
- `media_uploaded_at` — загрузка медиа подтверждена;
- `sidecars_uploaded_at` — sidecar-файлы загружены;
- `package_complete_at` — весь комплект проверен на стороне назначения;
- `delivery_failed_at` и код последней ошибки.

Наличие `delivered_at` не означает завершённую доставку.

### FR-024. Повторяемость и идемпотентность

- Каждый шаг pipeline имеет идемпотентный ключ.
- Повтор worker-задачи не создаёт скрытый дубль.
- Артефакт шага связан с версиями всех входов.
- При изменении входа зависимые шаги помечаются устаревшими.
- Нельзя продолжить доставку с устаревшими артефактами.

### FR-025. Аудит

Неизменяемый аудит должен фиксировать:

- загрузки и удаления локальных временных данных;
- создание и изменение сущностей;
- ручные исправления;
- смену статусов;
- утверждение и отклонение;
- выбор модели и промпта;
- создание мастера;
- запуск и результат доставки;
- обращения к секретам без записи самих секретов.

### 10.2. Требования к состояниям

- Отмена не удаляет уже созданные артефакты автоматически.
- Возврат на ранний этап инвалидирует зависящие от него результаты.

## 14. Рекомендуемая архитектура

```text
Web UI
  ↓
FastAPI application
  ├── PostgreSQL
  ├── Object Storage
  ├── Redis / task broker
  └── Worker orchestration
         ├── Media worker: FFmpeg/ffprobe
         ├── VLM worker: video understanding
         ├── Speech worker: ASR/alignment/TTS
         ├── Packaging worker
         └── Delivery worker: S3/GCS
```

### 14.1. Компоненты

#### Web UI

Рекомендуется React + TypeScript. Для самого раннего пилота допускается серверный UI или Gradio, но бизнес-логика не должна находиться внутри UI.

#### Backend

Рекомендуется Python 3.12+, FastAPI, Pydantic и SQLAlchemy/Alembic.

#### База данных

PostgreSQL для производственной версии. SQLite допускается только для локального прототипа и автоматических тестов.

#### Очередь

Redis с Celery, Dramatiq, RQ или другой утверждённой системой. Конкретный выбор фиксируется архитектурным решением до реализации production workers.

#### Объектное хранилище

S3-совместимое внутреннее хранилище или файловая система для пилота. Бинарные файлы не хранятся в PostgreSQL.

#### ML-адаптеры

```python
class VideoUnderstandingProvider: ...
class SpeechToTextProvider: ...
class WordAlignmentProvider: ...
class TextToSpeechProvider: ...
```

Бизнес-логика не должна напрямую зависеть от Qwen, Whisper или конкретного TTS.

### 14.2. Начальные реализации моделей

- VLM: локальная Qwen3-VL Instruct подходящего размера;
- ASR: faster-whisper;
- alignment: отдельный word-alignment backend либо подтверждённые word timestamps ASR;
- TTS: подключаемый локальный или облачный провайдер;
- scene detection: PySceneDetect;
- media processing: FFmpeg/ffprobe.

### 14.3. Развёртывание

MVP должен запускаться через Docker Compose:

```text
api
web
worker-media
worker-ml
worker-delivery
postgres
redis
object-storage (опционально для локальной среды)
```

GPU worker может разворачиваться на отдельном хосте. CPU-only режим обязан запускать приложение и тестовые fake providers, но не обязан обеспечивать приемлемую скорость реального VLM.

## 17. Безопасность

### 17.1. Доступ

- ролевая модель доступа;
- короткоживущие пользовательские сессии;
- защита endpoint'ов по ресурсу и заказчику;
- принцип минимальных привилегий;
- отдельные учётные данные workers.

### 17.2. Секреты

- секреты не хранятся открытым текстом в БД, `.env` репозитория или логах;
- использовать secret manager или защищённые переменные окружения;
- в интерфейсе показывать только наличие и последние безопасные символы;
- поддержать ротацию;
- предпочтительно использовать собственный сервис-аккаунт платформы, которому заказчик выдаёт ограниченный доступ, вместо хранения широкого ключа заказчика.

### 17.3. Медиа

- доступ к временным URL ограничен по времени;
- URL не записываются целиком в общие логи, если содержат подпись;
- политика хранения настраивается;
- удаление локальных копий выполняется отдельной подтверждаемой задачей после успешной поставки и окончания retention-периода;
- исходники и мастер-файлы не используются для обучения без отдельного правового основания.

### 17.4. Опасные операции

- платформа по умолчанию не удаляет и не перезаписывает данные заказчика;
- потенциально разрушительная административная операция требует конкретного списка объектов и отдельного подтверждения;
- такие операции всегда попадают в аудит.

## 18. Нефункциональные требования

### NFR-001. Надёжность

- Сбой worker не должен терять состояние задания.
- Все длительные шаги допускают безопасный retry.
- Система восстанавливается после перезапуска.
- Частично сформированный комплект нельзя принять за готовый.

### NFR-002. Производительность

Целевые показатели пилота:

- UI/API отвечает на обычный запрос не дольше 500 мс на p95 без учёта фоновой обработки;
- загрузка файла 1–6 ГиБ не требует его удержания в RAM;
- одновременно поддерживается минимум 3 активных задания, если хватает вычислительных ресурсов;
- обработка может быть медленнее длительности видео на CPU, но прогресс и состояние должны оставаться корректными;
- GPU throughput измеряется, а не фиксируется в SLA до выбора оборудования.

### NFR-003. Масштабирование

- workers масштабируются независимо по типу;
- GPU-задачи маршрутизируются только на подходящие workers;
- несколько API-инстансов не создают двойные задания;
- хранение файлов отделено от локального диска API.

### NFR-004. Наблюдаемость

- структурированные JSON-логи;
- correlation ID для запроса, job, package и delivery attempt;
- метрики длительности и ошибок каждого этапа;
- глубина очередей;
- использование CPU/GPU/RAM/VRAM;
- число комплектов по состояниям;
- алерт на застрявшие задания;
- секреты и полный текст чувствительных данных в логи не попадают.

### NFR-005. Совместимость

- серверная часть ориентирована на Linux;
- локальная разработка поддерживает macOS и Linux;
- медиаоперации воспроизводимы на закреплённой версии FFmpeg;
- версии моделей, библиотек и системных бинарников фиксируются.

### NFR-006. Локализация

- интерфейс MVP — русский;
- архитектура UI готова к английскому;
- язык контента не зависит от языка интерфейса.

### NFR-007. Доступность

- базовая навигация с клавиатуры;
- формы имеют подписи и явные сообщения об ошибках;
- статус не передаётся только цветом.

## 20. Критерии приёмки MVP

MVP принимается, если выполнены все условия:

1. Платформа разворачивается по документированной инструкции.
2. Оператор может загрузить MP4 размером не менее тестового целевого лимита.
3. Исходник сохраняется неизменным, его SHA-256 воспроизводим.
4. ffprobe-параметры отображаются в интерфейсе и сохраняются.
5. Точный дубль обнаруживается независимо от имени.
6. VLM возвращает валидируемое структурированное описание через provider interface.
7. Оператор может исправить заголовок, описание, категорию, главы и события.
8. Система поддерживает хотя бы два аудиорежима: сохранить исходную дорожку и заменить её озвучкой.
9. При замене звука видеопоток мастер-файла не перекодируется.
10. Транскрипт создаётся из текущего мастер-файла.
11. Каждое поставляемое слово имеет валидные `start` и `end`.
12. Отсутствие таймингов блокирует сборку или доставку кодом `no_word_timings`.
13. Метаданные строятся по версионируемой схеме и имеют заданный порядок ключей.
14. WPM, длительность и разрешение совпадают с поставляемыми артефактами.
15. Комплект проходит автоматический чек-лист.
16. После проверки можно получить ZIP с медиа, транскриптом, метаданными и манифестом.
17. Повтор шага с тем же idempotency key не создаёт дубль.
18. Состояния и ошибки видны в интерфейсе после перезапуска сервисов.
19. Есть аудит ручных исправлений и ключевых переходов.
20. Автоматические тесты проходят в CI.

Для релиза с облачной доставкой дополнительно:

21. Большое медиа передаётся resumable/multipart-механизмом.
22. Медиа всегда загружается до sidecar-файлов.
23. Существующий ключ не перезаписывается.
24. После загрузки хеши локального и удалённого файла сверяются.
25. `package_complete_at` устанавливается только после успешной сверки всего комплекта.

## 22. Требования к разработке Codex

### 22.1. Общие правила

- Реализовывать систему вертикальными срезами по этапам, а не создавать все интерфейсы заранее без рабочего pipeline.
- Перед каждым этапом фиксировать короткий план и критерии готовности.
- Не подменять внешние зависимости недокументированными решениями.
- Все рискованные допущения оформлять как ADR или открытый вопрос.
- Не добавлять облачный vendor lock-in в доменную модель.
- Не хранить секреты или реальные клиентские данные в репозитории.
- Не выполнять скрытое перекодирование мастер-видео.
- Не ослаблять блокирующие проверки ради прохождения happy path.

### 22.2. Требования к репозиторию

Рекомендуемая структура:

```text
apps/
  api/
  web/
workers/
  media/
  ml/
  delivery/
packages/
  domain/
  schemas/
  providers/
infra/
  docker/
  migrations/
tests/
  unit/
  integration/
  e2e/
docs/
  adr/
  api/
fixtures/
```

В корне должны находиться:

- `README.md`;
- `AGENTS.md` с командами и локальными правилами проекта;
- `.env.example` без секретов;
- `docker-compose.yml`;
- файл блокировки зависимостей;
- команды lint, typecheck, test и e2e;
- лицензии используемых моделей и библиотек либо ссылки на них.

### 22.3. Definition of Done для задачи

Задача завершена, если:

- реализован код;
- добавлены или обновлены тесты;
- обновлены схемы и миграции;
- обработаны ошибки и retry-сценарии;
- добавлена наблюдаемость для длительной операции;
- документация соответствует поведению;
- lint, typecheck и тесты проходят;
- нет секретов и больших бинарных файлов в Git;
- результат вручную проверен на релевантном fixture;
- соблюдена обратная совместимость либо описана миграция.

## 23. Открытые вопросы до начала production-разработки

Для первого реального заказчика необходимо письменно определить:

1. Какие файлы входят в обязательный комплект?
2. Нужен ли `manifest.json` заказчику или только платформе?
3. Какова точная схема и порядок полей метаданных?
4. Какой формат транскрипта принимается?
5. Какая точность word timings требуется?
6. Нужны ли главы?
7. Нужна ли подробная временная разметка действий или достаточно описания?
8. Каков закрытый справочник категорий и действий?
9. Разрешён ли синтетический голос?
10. Если требуется «человеческая озвучка», означает ли это содержание речи или происхождение голоса?
11. Что делать с исходным звуком камеры?
12. Допускается ли несколько аудиодорожек?
13. Как определяется `Publication Date`?
14. Как рассчитывается WPM: по полной длительности или только речевым интервалам?
15. Какая схема папок используется?
16. Как различать несколько ассетов одной темы?
17. Требуется ли клиентское шифрование?
18. Какой канал доставки и чьи credentials используются?
19. Кто выполняет приёмку и что считается браком?
20. Каков срок хранения исходников и промежуточных файлов?
21. Разрешено ли использовать материалы и исправления для дообучения?
22. Есть ли требования по географии хранения и обработке персональных данных?
23. Каковы целевые объёмы: файлов в день, длительность и максимальный размер?
24. Какое GPU-оборудование доступно?

Пока вопрос не закрыт, соответствующее поведение не должно кодироваться как неявное предположение. Оно оформляется конфигурацией или блокирующим условием запуска production-поставки.

## 24. Риски и меры снижения

| Риск | Мера |
|---|---|
| VLM выдумывает события | evidence, confidence, `unknown`, ручная проверка, эталонный набор |
| Быстрое действие пропущено между кадрами | адаптивная выборка, перекрытия, профиль высокой детализации |
| ASR даёт неточные слова | выбор модели, языковые профили, словари, ручная проверка |
| Тайминги слов неточны | отдельный forced alignment и метрика ошибки |
| Транскрипт не соответствует мастеру | связь с `master_sha256`, повторный ASR после изменения мастера |
| Перекодирование ухудшает видео | неизменяемость, `-c:v copy`, проверка stream hash/codec |
| Дубли с разными именами | SHA-256 |
| Перезапись в бакете | create-only semantics и preflight проверки |
| Частичная поставка выглядит завершённой | state machine, media-first, удалённая сверка |
| Потеря задания после сбоя | персистентная очередь, checkpoints, идемпотентность |
| Утечка credentials | secret manager, минимальные права, маскирование логов |
| Vendor lock-in | provider interfaces и канонические внутренние схемы |
| Автоматизация неверного формата | ручной пилот и письменная приёмка до построения потока |

## 25. Стратегия обучения моделей

### 25.1. До пилота

Обучение собственной модели не выполняется. Используются готовые модели и строгие структурированные промпты.

### 25.2. Сбор обучающих данных

Для каждого запуска сохраняются:

- клип или ссылка на его неизменяемую версию;
- хеш видео;
- машинный ответ;
- версия модели;
- версия промпта;
- исправленный оператором ответ;
- QA-решение;
- причина исправления;
- разрешение на использование в обучении.

### 25.3. Условия начала fine-tuning

LoRA/QLoRA рассматривается, если:

- накоплено достаточно разрешённых качественных примеров;
- ошибки повторяются и не устраняются схемой или промптом;
- есть отдельные train/validation/test по исходным видео;
- определены измеримые целевые метрики;
- стоимость поддержки модели оправдана сокращением ручной работы.

### 25.4. Правила разделения данных

- Фрагменты одного исходного видео не могут попадать в разные split'ы.
- Тестовый набор фиксируется до обучения.
- Данные конкретного заказчика не смешиваются с другими без разрешения.
- Негативные примеры и `unknown` обязательны.
- Результат новой модели сравнивается с базовой на одном и том же наборе.

### 25.5. Целевая задача обучения

Приоритет — узкая адаптация:

```text
видео конкретного домена
→
метаданные, события и сценарий по конкретной утверждённой схеме
```

Обучение универсальной video-language model с нуля не входит в план.

## 26. Итоговый критерий продукта

Платформа успешна, если оператор может превратить исходное видео в проверенный комплект без ручной работы с именами файлов, JSON, FFmpeg, хешами и облачными командами, при этом каждое автоматически принятое решение воспроизводимо, каждый артефакт связан со своим источником, а статус «доставлено» подтверждается фактическим наличием и целостностью файлов у заказчика.
